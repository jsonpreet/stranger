## 1. Executive Summary

Stranger is a self-hosted PaaS platform (Coolify-style) built for speed and operational simplicity. The core thesis is **speed by subtraction** — precompiled deploy plans, static routing, hash-based builds, and single-binary Go agents eliminate the runtime decision-making that makes comparable platforms slow.

The project has completed **Phases 0, 1, 2** and the **V2 Hardening Sprint** and now sits at a solid MVP baseline with authentication, a durable job queue, secrets encryption, and a functional Next.js dashboard.

## 2. Architecture Overview

```
User Browser
    │
    ▼
Dashboard (Next.js 16, React 19) — :3301
    │  API Proxy (Next.js route handlers)
    ▼
Control Plane (Go) — :8080
    │  Bearer token auth   Job Queue (SQLite WAL)
    ▼
Agent (Go) — :3000
    │  X-Agent-Token auth  Docker API
    ▼
Containers + Caddy Router
```

**Three-tier, no Kubernetes, no Swarm.** The deploy path is the shortest path.

### 3.5 Secrets Engine

- **Algorithm:** AES-256-GCM with random 12-byte nonce
- **Key format:** 32-byte raw key or `base64:`-prefixed base64 string
- **Ciphertext format v1:** `v1:<base64(nonce+ciphertext)>` (legacy, key-ID-less)
- **Ciphertext format v2:** `v2:<key_id>:<base64(nonce+ciphertext)>`
- **Keyring:** Multiple named keys; primary key ID governs encryption; all keys can decrypt
- **Rotation:** `POST /admin/secrets/rotate` supports `dry_run: true`; dispatcher auto-rotates on access
- **Config:** `STRANGER_SECRETS_KEY` (single) or `STRANGER_SECRETS_KEYS=k1=<mat>,k2=<mat>` + `STRANGER_SECRETS_PRIMARY_KEY_ID`

## 5. Gap Analysis

### 5.1 Critical (blocking production readiness)

| Gap | Details |
|-----|---------|
| **Build hash caching** | `GeneratePlan` creates a new UUID every time; no `template+git_sha+env_hash+lockfile_hash` fingerprint. Every deploy is a full rebuild. |
| **Deploy retry / timeout** | Dispatcher dispatches once with no retry on transient agent errors. `AttemptCount` is tracked but not acted on. |
| **Agent graceful shutdown** | Agent `main.go` uses `ListenAndServe` with no signal handling. In-flight deploys are lost on SIGTERM. |
| **Health-check-driven rollout** | No readiness check before routing traffic to new container. |
| **Rollback** | No rollback endpoint or mechanism exists yet; UI button is planned but missing. |
| **Single agent, single server** | No multi-agent registry; `STRANGER_AGENT_URL` is a single static URL. |

### 5.2 Security

| Gap | Details |
|-----|---------|
| **No RBAC** | Only one API token for all access; no user-level auth on control plane (user auth is dashboard-only). |
| **No rate limiting** | All endpoints are unthrottled. |
| **Deploy token not scoped** | Agent token is global; there is no per-job short-lived token as described in the security model. |
| **Secret redaction in logs** | Secrets are passed as container env vars; no scrubbing of log streams. |
| **Container hardening** | No read-only FS, no capability dropping, no network isolation between app containers. |
| **Caddy config path validation** | `caddy.go` writes to a local file; path should be validated to prevent directory traversal in edge cases. |

### 5.3 Reliability

| Gap | Details |
|-----|---------|
| **No agent heartbeat** | Control plane has no visibility into agent health between deploys. |
| **No log backpressure** | `io.Copy` on log stream; no max-bytes limit if container logs are very large. |
| **No job TTL or cleanup** | `deploy_jobs` and `audit_events` tables grow unbounded. |
| **SQLite single-writer** | `MaxOpenConns(1)` is correct for SQLite; documented limitation for future multi-writer needs. |

### 5.4 DX / Observability

| Gap | Details |
|-----|---------|
| **No structured deploy history in UI** | Deploy jobs exist in DB but deploy history UI screen (`/deployments`) is a placeholder. |
| **No metrics** | No Prometheus/OpenTelemetry integration. |
| **No webhook trigger** | No git webhook endpoint; deploys are manually triggered only. |

## 7. Recommended Next Steps (Priority Order)

1. **Build hash caching** — Implement `sha256(template+git_sha+env_hash+lockfile_hash)` in `GeneratePlan`; skip build if image tag exists in Docker. This is the single highest-leverage performance win.

2. **Rollback endpoint + UI** — Add `POST /deploy/rollback` that switches the Caddy route to a previous stable image tag. Unblock the rollback UI button.

3. **Agent graceful shutdown + retry** — Add `signal.NotifyContext` to agent, drain in-flight goroutines, add dispatcher retry with backoff for transient failures.

4. **Health-check-driven rollout** — After container starts, poll the container's port before updating the Caddy route. If health check fails, roll back automatically.

5. **Job cleanup / TTL** — Add a background goroutine to purge `deploy_jobs` and `audit_events` older than N days.

6. **Per-job deploy tokens** — Issue short-lived, scoped tokens for each dispatch instead of reusing the global agent token.

7. **Git webhook endpoint** — `POST /webhooks/github` to auto-trigger deploys on push, matching the "git push → live app" north star.

8. **Agent heartbeat** — Add `POST /internal/agent/heartbeat` so control plane knows agent is alive.

9. **Metrics** — Add Prometheus counters for deploy durations, queue depth, build cache hit/miss.

10. **Multi-server support** — Agent registry in SQLite; dispatcher routes jobs to registered agents.

## 9. Summary

Stranger has a clean, well-structured foundation. The core deploy path works end-to-end: create project → queue job → dispatch plan → build image → run container → update Caddy → stream logs → callback status. Authentication and secrets are properly implemented. The dashboard provides a complete onboarding and project management UX.

The main gaps are build caching (the biggest performance win), rollback, retry/resilience, and production hardening (RBAC, rate limiting, container security). The project is at a solid **pre-alpha / internal demo** quality level and needs the Phase B (reliable pipeline) work to be ready for external use.
