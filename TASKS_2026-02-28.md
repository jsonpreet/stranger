## 🔴 Critical (Blocking Production)

### T-01 — Build hash caching
**Status:** Not started
**Description:** Every deploy triggers a full Docker rebuild. `GeneratePlan` generates a new UUID on every call with no fingerprinting. Need to implement `sha256(template + git_sha + env_hash + lockfile_hash)` so if the hash already exists as a Docker image tag, the build step is skipped entirely.
**Impact:** Cached deploy target is < 2s. Currently every deploy is equivalent to a fresh build.
**Files:** `services/control-plane/internal/deployer/deployer.go`, `services/agent/internal/builder/builder.go`

---

### T-02 — Rollback endpoint + UI
**Status:** Not started
**Description:** No rollback mechanism exists. The deploy plan tracks `plan_id` in `deploy_jobs` but there's no endpoint to switch the Caddy route back to a previous stable image. The dashboard has a rollback button placeholder that goes nowhere.
**Impact:** Any failed deploy leaves the service in a broken state with no recovery path.
**Files:** `services/control-plane/main.go`, `services/agent/internal/router/caddy.go`, `apps/dashboard/components/project-details-client.jsx`

---

### T-03 — Agent graceful shutdown
**Status:** Not started
**Description:** Agent `main.go` calls `server.ListenAndServe()` with no signal handling. A SIGTERM during a deploy goroutine silently kills the in-flight build/deploy, leaving the job stuck in `dispatched` or `running` state in the control plane forever.
**Impact:** Any restart (deploy, system update) corrupts in-flight job state.
**Files:** `services/agent/main.go`

---

### T-04 — Deploy retry with backoff
**Status:** Not started
**Description:** Dispatcher dispatches a job once. If the agent returns an error (transient network, Docker daemon hiccup), the job is immediately marked `failed` with no retry. `attempt_count` is tracked in the DB but never acted on.
**Impact:** Flaky deploys fail permanently instead of recovering automatically.
**Files:** `services/control-plane/internal/queue/dispatcher.go`

---

### T-05 — Health-check-driven rollout
**Status:** Not started
**Description:** After a container starts, the agent immediately updates the Caddy route without verifying the app is actually listening. If the app crashes on startup, traffic is routed to a dead container.
**Impact:** Silent broken deploys — the deploy reports `succeeded` but the app is not serving traffic.
**Files:** `services/agent/main.go`, `services/agent/internal/container/manager.go`

## 🟠 Security Issues

### S-01 — No RBAC / user-level auth on control plane
**Status:** Not started
**Description:** The control plane uses a single global `STRANGER_API_TOKEN`. Anyone with this token has full admin access. The user auth (login/register) lives only in the dashboard layer with no enforcement at the API level. No owner/admin/viewer roles exist.
**Files:** `services/control-plane/main.go`

---

### S-02 — Global agent token (not scoped per job)
**Status:** Not started
**Description:** The same `STRANGER_AGENT_TOKEN` is reused for every deploy dispatch, log proxy, and callback. The security model calls for short-lived, per-job deploy tokens. A leaked agent token gives permanent access.
**Files:** `services/control-plane/internal/queue/dispatcher.go`, `services/agent/main.go`

---

### S-03 — No rate limiting
**Status:** Not started
**Description:** All endpoints (including `/deploy` and `/auth/*`) have no rate limiting. An attacker with the API token can flood the deploy queue or brute-force attempt credential endpoints.
**Files:** `services/control-plane/main.go`, `apps/dashboard/app/api/auth/`

---

### S-04 — Secret values visible in container env / logs
**Status:** Not started
**Description:** Secrets are decrypted and injected as plain `Env` map values in the deploy plan, then passed directly to Docker as container env vars. No scrubbing of log streams if an app accidentally prints env vars. Log output is forwarded as-is.
**Files:** `services/control-plane/internal/queue/dispatcher.go`, `services/agent/internal/logs/streamer.go`

---

### S-05 — No container security hardening
**Status:** Not started
**Description:** Containers are started with default Docker security settings. The project's own security model requires: read-only FS where possible, dropped Linux capabilities, network isolation between app containers, and binding internal ports to localhost only (proxied through Caddy).
**Files:** `services/agent/internal/container/manager.go`

## 🟡 Reliability Issues

### R-01 — No agent heartbeat
**Status:** Not started
**Description:** Control plane has no way to know if the agent is alive between deploys. If the agent process dies, the next deploy is dispatched to a dead endpoint, fails, and the user sees a generic agent error with no indication of the root cause.
**Files:** `services/control-plane/main.go`, `services/agent/main.go`

---

### R-02 — Jobs and audit events grow unbounded
**Status:** Not started
**Description:** `deploy_jobs` and `audit_events` tables have no TTL or cleanup policy. On a busy instance these will grow indefinitely and degrade SQLite query performance over time.
**Files:** `services/control-plane/internal/store/sqlite.go`

---

### R-03 — Stuck jobs (dispatched/running with no timeout)
**Status:** Not started
**Description:** If the agent crashes mid-deploy after reporting `running`, the job stays `running` forever. There is no timeout or watchdog to move stale jobs to `failed`.
**Files:** `services/control-plane/internal/queue/dispatcher.go`, `services/control-plane/internal/store/sqlite.go`

---

### R-04 — No log stream size limit
**Status:** Not started
**Description:** `io.Copy` on log streams has no byte cap. If a container produces extremely large output the stream will consume unbounded memory/bandwidth.
**Files:** `services/control-plane/main.go` (log proxy), `services/agent/internal/logs/streamer.go`

---

### F-02 — Deploy history UI
**Status:** Not started
**Phase:** Phase 2 / Phase B
**Description:** Deploy jobs exist in the DB and the `/deployments` route exists in the dashboard, but the page is a placeholder stub. Needs a real timeline view with status, duration, plan ID, and log links.

### F-03 — Disk cleanup (old images + containers)
**Status:** Not started
**Phase:** Phase 3
**Description:** Every deploy builds a new Docker image. Old images and stopped containers are never removed. On any real server this will exhaust disk space within days of active use.
**Files:** `services/agent/internal/builder/builder.go`, `services/agent/internal/container/manager.go`

---

### F-04 — Backup / restore
**Status:** Not started
**Phase:** Phase 3
**Description:** No backup mechanism for the SQLite DB or Caddy config. A disk failure loses all project + secret data.

### F-05 — Node reconnection logic

**Phase:** Phase 3
